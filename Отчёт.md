# Отчёт по приложению «Focus»

## 1. Доменная область приложения

«Focus» — простое клиент-серверное веб-приложение для персонального управления задачами. Пользователь может создать задачу, указать её название и описание, посмотреть список задач, изменить задачу, отметить её выполненной и удалить.

Приложение решает базовую задачу ведения списка дел. Оно выбрано как основа для последующих работ по контейнеризации, оркестрации, балансировке, мониторингу и обеспечению отказоустойчивости.

### Пользовательские сценарии

1. Пользователь открывает веб-страницу и получает актуальный список задач.
2. Пользователь создаёт задачу с обязательным названием и необязательным описанием.
3. Пользователь редактирует название, описание или состояние выполнения.
4. Пользователь удаляет ненужную задачу.
5. После перезагрузки страницы данные сохраняются, поскольку находятся в PostgreSQL.

## 2. Стек реализации

### Бэкенд

- Go 1.23;
- стандартная библиотека `net/http` для HTTP/1.1-сервера и маршрутизации;
- `encoding/json` для сериализации данных;
- `log/slog` для структурированных JSON-логов;
- `context` для отмены операций и таймаутов;
- `pgx/v5` для подключения к PostgreSQL.

Бэкенд не использует тяжёлый веб-фреймворк или ORM. Это уменьшает количество зависимостей и потребление ресурсов, а SQL-запросы остаются явными и понятными.

### Фронтенд

- HTML5;
- CSS3;
- JavaScript;
- Fetch API для взаимодействия с REST API.

Статические файлы встраиваются в Go-бинарник с помощью `go:embed`. Отдельный Node.js-процесс или веб-сервер для фронтенда не требуется.

### Хранение данных и инфраструктура

- PostgreSQL 17;
- Podman и OCI-контейнеры;
- multi-stage `Containerfile`;
- Makefile для воспроизводимого локального запуска;
- Compose-файл как альтернативное декларативное описание окружения;
- Git и GitHub для контроля версий.

## 3. Архитектура

Приложение имеет трёхуровневую структуру:

```text
Браузер пользователя
        │ HTTP/JSON
        ▼
Go HTTP-сервер
  ├── встроенный фронтенд
  ├── REST-обработчики
  └── PostgreSQL-репозиторий
        │ SQL
        ▼
PostgreSQL
```

Основные каталоги проекта:

```text
cmd/server              запуск HTTP-сервера и управление его жизненным циклом
cmd/migrate             одноразовый административный процесс миграции
internal/config         загрузка конфигурации из переменных окружения
internal/database       подключение к PostgreSQL и применение миграций
internal/tasks          доменная модель, репозиторий и HTTP-обработчики
internal/webui/assets   HTML, CSS и JavaScript фронтенда
```

Сервер и мигратор собираются в два независимых исполняемых файла. Сервер не изменяет схему базы при запуске. Миграции выполняются отдельным процессом перед запуском новой версии приложения.

## 4. Основные сущности доменной области

### Task — задача

Главная сущность приложения содержит следующие поля:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `BIGSERIAL` | Уникальный идентификатор |
| `title` | `TEXT` | Обязательное название длиной до 200 символов |
| `description` | `TEXT` | Необязательное описание |
| `completed` | `BOOLEAN` | Признак выполнения |
| `created_at` | `TIMESTAMPTZ` | Время создания |
| `updated_at` | `TIMESTAMPTZ` | Время последнего изменения |

Ограничения проверяются на двух уровнях: в Go-коде перед выполнением запроса и в схеме PostgreSQL.

### SchemaMigration — применённая миграция

Служебная сущность `schema_migrations` хранит имена уже применённых SQL-миграций. Благодаря этому мигратор можно запускать повторно: выполненные миграции не применяются ещё раз.

## 5. CRUD и HTTP API

Взаимодействие фронтенда с бэкендом выполняется по HTTP/1.1 в формате JSON.

| Операция | Метод и путь | Результат |
|---|---|---|
| Create | `POST /api/tasks` | Создаёт задачу |
| Read | `GET /api/tasks` | Возвращает список задач |
| Update | `PUT /api/tasks/{id}` | Обновляет задачу |
| Delete | `DELETE /api/tasks/{id}` | Удаляет задачу |
| Health check | `GET /healthz` | Проверяет сервер и соединение с БД |

Пример тела запроса на создание или обновление:

```json
{
  "title": "Изучить Go",
  "description": "Разобраться с REST API",
  "completed": false
}
```

API проверяет обязательность и длину названия, корректность идентификатора и ограничивает размер тела HTTP-запроса. Ошибки возвращаются в JSON с соответствующим HTTP-кодом.

## 6. Соответствие методологии Twelve-Factor App

### I. Codebase — одна кодовая база

Исходный код приложения хранится в одном Git-репозитории. Один и тот же репозиторий может использоваться для нескольких развёртываний: локального, тестового и production. Отличия между окружениями не требуют создания копий исходного кода.

### II. Dependencies — явные и изолированные зависимости

Go-зависимости явно перечислены в `go.mod`, а точные контрольные суммы находятся в `go.sum`. Сборка выполняется внутри официального Go-образа. Runtime-окружение изолировано OCI-контейнером и не зависит от установленного на хостовой машине Go SDK.

### III. Config — конфигурация в окружении

Настройки не зашиты в исходный код и считываются из переменных окружения:

- `PORT` — HTTP-порт;
- `DATABASE_URL` — строка подключения к PostgreSQL;
- `SHUTDOWN_TIMEOUT` — время graceful shutdown.

Файл `.env.example` содержит только пример конфигурации. Настоящий `.env` исключён через `.gitignore` и не попадает в репозиторий.

### IV. Backing services — внешние ресурсы

PostgreSQL рассматривается как подключаемый внешний ресурс. Приложение знает только значение `DATABASE_URL`. Локальный контейнер PostgreSQL можно заменить облачной или отказоустойчивой БД без изменения Go-кода.

### V. Build, release, run — разделение стадий

- **Build:** multi-stage `Containerfile` запускает тесты и компилирует два бинарника.
- **Release:** отдельный бинарник `/app/migrate` применяет версионированные миграции.
- **Run:** `/app/server` запускает уже собранное приложение и не изменяет схему БД.

В `make up` эти действия выполняются последовательно: build → database → migrate → app.

### VI. Processes — процессы без состояния

HTTP-сервер не сохраняет пользовательские данные в памяти или локальных файлах. Всё постоянное состояние хранится в PostgreSQL. Любой экземпляр сервера может обработать любой запрос, поэтому потеря контейнера не приводит к потере задач.

### VII. Port binding — экспорт сервиса через порт

Приложение самостоятельно запускает HTTP-сервер и слушает порт из переменной `PORT`. Для работы ему не требуется внешний application server. Контейнер публикует порт 8080.

### VIII. Concurrency — масштабирование процессами

Сервер является stateless, поэтому можно запустить несколько одинаковых контейнеров и распределять запросы через балансировщик. Каждый экземпляр использует собственный пул соединений с общей PostgreSQL. Сервер также обрабатывает каждый HTTP-запрос конкурентно средствами Go runtime.

### IX. Disposability — быстрый старт и корректное завершение

Бинарник запускается без длительной локальной инициализации. Приложение обрабатывает `SIGINT` и `SIGTERM`, прекращает принимать новые запросы и ожидает завершения активных запросов в пределах `SHUTDOWN_TIMEOUT`. Это позволяет безопасно заменять экземпляры приложения.

### X. Dev/prod parity — сходство окружений

Локально и в production предполагается использовать один и тот же OCI-образ приложения и PostgreSQL. Для запуска не используются локальные mock-хранилища или альтернативная СУБД. Различия окружений задаются конфигурацией, а не изменениями исходного кода.

### XI. Logs — логи как поток событий

Приложение не создаёт и не ротирует файлы логов. Структурированные JSON-события записываются в stdout. Podman, Kubernetes или система централизованного логирования могут самостоятельно собирать и хранить этот поток.

### XII. Admin processes — административные задачи

Миграции оформлены как отдельный одноразовый процесс `/app/migrate`, собранный из той же кодовой базы и использующий ту же конфигурацию подключения. В Kubernetes этот процесс может запускаться как Job.

## 7. Запуск приложения

Для локального запуска требуются Podman и Make:

```bash
podman machine start
make up
```

После запуска интерфейс доступен по адресу <http://localhost:8080>. Посмотреть структурированные логи можно командой:

```bash
make logs
```

Остановка контейнеров:

```bash
make down
```

Volume с данными PostgreSQL сохраняется между запусками.

## 8. Проверка

Во время сборки образа выполняется `go test ./...`. Модульные тесты проверяют создание задачи, валидацию обязательного названия и обновление сущности через HTTP API. Дополнительно было вручную проверено полное прохождение CRUD-сценария с PostgreSQL: создание, чтение, обновление и удаление задачи.

## 9. Итог

Реализовано полноценное минимальное клиент-серверное приложение с фронтендом, REST-бэкендом и PostgreSQL. Все CRUD-операции доступны пользователю через веб-интерфейс и HTTP API. Приложение соответствует двенадцати факторам и готово к дальнейшим работам: развёртыванию в Kubernetes, подключению Prometheus и Grafana, централизованному сбору логов и настройке отказоустойчивой PostgreSQL.
